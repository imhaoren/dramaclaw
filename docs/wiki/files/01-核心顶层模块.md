# 核心顶层模块（`src/novelvideo/*.py`，54 个）

这一层是全仓的「公共底座」：存储、配置、模型网关、数据模型、前置条件、用量记账、网关遥测。没有业务路由，但几乎所有路由都依赖它们。

阅读顺序建议：`config.py` → `models.py` → `sqlite_store.py` → `task_state.py` → `project_config.py` → 其余按需。

---

## A. 存储与状态（8）

#### `sqlite_store.py` · 3,221 行 `[核实]`

**作用**：项目级 SQLite 的唯一读写门面。只做 SQLite，不引入 Cognee/图谱依赖，供 API、任务、验证系统共用。

**接口**：`SQLiteStore`（连接管理、`list_/get_/upsert_/delete_` 系列）；`load_episode_planning_content()`；`reset_path_repair_state()`。
**I/O**：读 `data.db` 的 `characters/episodes/beats/scenes/props/story_analysis_*` → 写同库；不碰文件系统。
**依赖**：`sqlite_schema`/`sqlite_pragmas` 建连；`models` 做类型映射；被 `cognee/store.py`、几乎所有路由、`runners/*` 调用。
**注意**：它是这些表的**唯一写入方**，绕过它直接写库会让索引 sidecar 与缓存不一致；不提供跨表事务 API，复杂写入要自己开事务。

#### `task_state.py` · 1,851 行 `[核实]`

**作用**：任务状态持久化。解决「worker 退出后结果取不到」的核心问题。

**接口**：`TaskStateManager`（`reserve/start/finish/fail/cancel/list/get`）；`TaskState`；`get_task_manager()`；`compute_expiry()`；`project_task_run_context()`（任务内取当前 task id 的上下文变量）。
**I/O**：读写 `task_states`（22 列）；DB 路径按项目解析（`get_project_task_db_path`）。
**依赖**：`project_context`、`task_identity`、`task_backend.queues`；被 `runners/*`、`api/routes/tasks.py`、`chat/director_auto.py` 调用。
**注意**：状态集合 `ACTIVE_PROJECT_TASK_STATUSES` / `TERMINAL_TASK_STATUSES` 是配额判定的依据，新增状态必须同步这两处，否则配额会计错。

#### `sqlite_schema.py` · 222 行 `[核实]`

**作用**：跨进程串行化建表与版本登记，避免多 worker 同时 `CREATE TABLE` 打架。

**接口**：`ensure_sqlite_schema()`、`mark_schema_component()`、`schema_component_is_current()`、`sqlite_schema_lock()`。
**I/O**：读写 `novelvideo_schema_components(component, version)`；用文件锁 `schema_lock_path()`。
**注意**：迁移契约是「每张表自己负责 `CREATE TABLE IF NOT EXISTS` + 幂等升级」，这里只负责串行与记账，不是迁移框架。

#### `sqlite_pragmas.py` · 60 行 `[核实]`

**作用**：统一连接参数（WAL、`busy_timeout`、`synchronous`），并提供 Litestream 开关判断。

**接口**：`configure_sqlite_connection()`、`configure_sqlite_connection_async()`、`litestream_enabled()`。
**注意**：所有建连都应走这里；自己 `sqlite3.connect()` 不开 WAL 会导致并发读写互相阻塞。

#### `project_config.py` · 575 行 `[核实]`

**作用**：项目级配置（`project_config.json`）的原子读改写。含风格、旁白、模型绑定、`project_uuid` 保障。

**接口**：`load_project_config()`、`update_project_config_file()`、`ensure_project_uuid()`、`load_narration_style()`、`load_narrator_reference_audio()`、`update_regen_file_map()`。
**I/O**：读写 `state/<user>/<project>/project_config.json`（临时文件 + rename 原子替换）。
**注意**：并发写会丢更新，必须走 `update_*` 系列而不是自己读-改-写；`ensure_cognee_embedding_binding` 只对 legacy 管线有意义。

#### `task_identity.py` · 198 行 `[核实]`

**作用**：任务标识的规范化。把「作用域 + 类型 + 目标」压成稳定的 `task_key`。

**接口**：`task_state_key()`、`project_task_state_key()`、`task_scope_from_key()`、`selection_scope()`、`hashed_scope()`、`actor_name_for_task()`。
**注意**：`task_key` 是幂等的基础——同一目标重复提交会复用同一行。需要"再来一次"时必须换 scope，否则会读到旧结果。

#### `task_scopes.py` · 18 行 `[核实]`

**作用**：三个常用 scope 的稳定构造：`prop_reference_asset_scope`、`scene_reference_asset_scope`、`stage_asset_scope`。
**注意**：scope 字符串进 `task_key` 哈希，改名等于让历史任务失联。

#### `task_jobs.py` · 203 行 `[核实]`

**作用**：给 Skill/Agent 用的任务编排助手：投递、等终态、读结果。

**接口**：`start_sketch_edit_execute_job()`、`wait_for_task_terminal()`、`read_task_result()`、`load_project_skill_env()`。
**注意**：`wait_for_task_terminal` 有超时；不要在请求线程里无限等。

## C. 数据模型与结构化抽取（12）

#### `project_context.py` · 154 行 `[核实]`

**作用**：新代码里**唯一的项目身份对象**。把"项目是谁、用户是谁、扮演什么角色、home 节点在哪"收敛成一个值对象，替代过去到处传 `project_id` / `user_id` 两个裸字符串的做法。

**接口**：
- `ProjectContext`：值对象（项目、用户、角色、home 节点）
- `resolve_project_context()`：从请求/任务上下文构造
- `require_project_role()`：角色不足直接抛错
- `require_project_home_node()` / `is_record_home_node()`：home 节点校验（画布节点的归属判据）
- `user_id_from_api_user()`：从 API 用户对象取稳定 user id

**I/O**：读鉴权上下文与项目注册表 → 产出 `ProjectContext`；角色不足抛异常。

**依赖**：被路由层与任务 runner 广泛调用（`task_identity`、`task_backend.queues` 同层）。

**使用场景**：任何新增端点或 runner，第一件事就是 `resolve_project_context()`，不要自己去查库拼 project/user。

**注意**：
1. 这是"**唯一**"身份对象——新代码里再出现 `def f(project_id: str, user_id: str)` 这种签名就是在绕它，会把角色校验漏掉。
2. `require_project_home_node()` 是画布归属的判据，与 [09-画布Freezone](../09-画布Freezone.md) 的 home node 守卫是同一套语义；改这里等于改画布权限。
3. 角色校验在**后端**；前端的 `lib/project-permissions.ts` 只做 UI 隐藏，不是权限。
