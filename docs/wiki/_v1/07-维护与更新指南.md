# 07 · 维护与更新指南

> Wiki 的价值不在"写完那一刻"，而在"三个月后还准"。
> 本篇定义：**谁在什么时候必须改哪一段**，以及怎么低成本验证。

---

## 1. 三条维护原则

| 原则 | 含义 | 反面案例 |
|---|---|---|
| **同 commit 更新** | 改代码的那个 PR 里就把对应 Wiki 章节改掉，不留"后续补文档"的 issue | 新任务类型上线了，[03 §3.1](03-核心功能与流程.md#31-任务类型清单28-种) 还是旧的 28 种 |
| **单一事实源** | Wiki 只做"整合视图"，不复制权威内容。环境变量的权威是 `.env.example`，视觉的权威是 `DESIGN.md`，依赖的权威是 `uv.lock` | 在 Wiki 里抄一份完整 env 表，然后它与 `.env.example` 漂移 |
| **可验证** | 每个结论尽量落到"能用一条命令验证" | 写"支持 Node 18+"但没写怎么查 |

**推论**：Wiki 里凡是「表格 + 数字」（任务类型数、表数、端口、版本）都是**易腐点**，改动时应优先检查。

## 3. 新增一篇 Wiki 页面的模板

```markdown
# NN · 页面标题

> 一句话说明本篇解决什么问题、不解决什么。

---

## 1. 第一节
（正文；能用表格就用表格，能用图就用 mermaid）

## 2. 第二节
...

## 维护提示

| 改动 | 需同步更新 | 校验 |
|---|---|---|
| ... | ... | ... |

_最后更新：YYYY-MM-DD_
```

约定：

1. **编号即顺序**：`01`…`07` 表示推荐阅读顺序，新增插在末尾或重排编号（同时改 [首页索引](README.md) 与所有入链）。
2. **每篇结尾必须有「维护提示」表**，这是本篇的"腐化防护"。
3. **每篇结尾写「最后更新」日期**，不写"作者"（git 有记录）。
4. **mermaid 图控制在 20 行内**，超过就拆图；GitHub、IDE 预览、多数 wiki 引擎都能渲染。
5. **相对链接**用 `文件名.md#锚点`，不要写绝对 URL（换仓库/换域名就废）。

## 5. 文档质量门禁

本 Wiki 不引入额外工具链，复用仓库既有的三条门禁 + 两条人工检查：

| 检查 | 方式 | 通过标准 |
|---|---|---|
| 内部链接 | 手工/编辑器预览 | 所有 `xx.md#anchor` 可跳转 |
| 代码块可执行 | 在干净环境跑一遍 | 命令不报"command not found" |
| 与代码一致性 | 对照 §4 易腐点表 | 数字与命令输出一致 |
| 术语一致 | 对照 [01 §2](01-项目概述.md#2-三个名字别搞混) | 不混用 DramaClaw / novelvideo / supertale |
| 双语同步 | 若同时改 `docs/zh` 与 `docs/en` | 两版语义一致（Wiki 本身只维护中文） |

**CI 相关**（已有，Wiki 变更不应破坏）：

```bash
pre-commit run --all-files          # gitleaks 等
uv run pytest                       # 默认排除 ee / e2e
npx @google/design.md lint DESIGN.md
```

## 6. 归档与演进

| 场景 | 处理 |
|---|---|
| 某个子系统被移除（如 Cognee 旧路径） | 不删章节，加 `> ⚠️ 已废弃（vX.Y）` 标记并说明替代方案，保留一两个大版本 |
| 大重构 | 先更新 [02 目录结构](02-目录结构与模块划分.md)，再更新流程页，最后回头校首页索引 |
| Wiki 与对外文档冲突 | **以代码为准**，两边都改；对外文档（`docs/zh`）优先面向用户措辞，Wiki 优先面向实现细节 |
| 新增语言版本 | 在 `docs/wiki/` 下开子目录（如 `en/`），首页加语言切换行，不要在同文件内混排 |
