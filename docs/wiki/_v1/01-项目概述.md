# 01 · 项目概述与目标

> 本篇回答三个问题：它是什么、它想解决什么、它刻意不做什么。

---

## 1. 一句话定位

**DramaClaw 是一条可自托管的「AI 短剧生产流水线」**：丢进一部小说原稿或剧本，它负责结构化拆解、分集规划、剧本生成、角色/场景/道具资产生成、分镜与首帧、逐镜视频与配音，最终合成带字幕的成片；同时提供一块**无限节点画布**用于自由探索，两者共享同一套资产库与同一个 Agent。

它不是一个「模型聚合玩具」，而是作者团队日常在用的生产线——这句话直接写在 README 开头，也解释了为什么代码里有大量看似过度严谨的工程约束（任务信封签名、断点续跑、质量门禁、CE/EE 端口隔离）。

---

## 2. 三个名字，别搞混

初读代码最容易踩的坑：项目对外叫 DramaClaw，但代码、目录、包名都还是历史名。

| 出现位置 | 名字 | 说明 |
|---|---|---|
| README / 用户界面 / 发行物 | **DramaClaw** | 对外品牌 |
| `pyproject.toml` `[project].name` | `supertale-ce` | 发行包名（SuperTale Community Edition） |
| `src/` 下唯一包目录 | `novelvideo` | Python 导入根，CLI 入口 `novelvideo` |
| `frontend/package.json` | `supertale-fe` | 前端包名 |
| 环境变量 | `ST_*` / `NOVELVIDEO_*` / `DRAMACLAW_*` / `SUPERTALE_*` | **四套前缀并存**，均为合法配置入口，见 [04](04-依赖与配置说明.md) |

> 记忆法：**产品叫 DramaClaw，后端叫 novelvideo，发行叫 supertale-ce，前端叫 supertale-fe。** 环境变量前缀的混用是历史遗留，读取时通常按 `DRAMACLAW_ → SUPERTALE_ → NOVELVIDEO_` 优先级回落（例如 `chat.service._chat_backend`）。

## 3. 项目目标

### 3.1 要解决的问题

传统「AI 做视频」的工作流是十几个割裂工具的拼接：写作工具 → 绘图工具 → 视频工具 → 配音工具 → 剪辑软件 → 网盘。每一跳都要手工搬素材、手工对命名、手工保证角色长得一样。

DramaClaw 的目标是把这条链路**收敛成一条有状态的流水线**：

| 痛点 | DramaClaw 的应对 |
|---|---|
| 角色跨镜头「不是同一个人」 | 身份（identity）资产 + 参考图 + 单集变体，绑定到 beat 级引用 |
| 分集/分场靠人脑记 | `episodes` / `beats` / `scenes` 结构化落库，前端按集工作台组织 |
| 长任务中断即从头再来 | 任务状态机 + checkpoint 续跑 + 任务中心取消/重试 |
| 素材散落在各工具目录 | 统一资产库（角色/场景/道具/音色），画布与流水线共享 |
| 换模型要改一套代码 | 全部走 OpenAI 兼容网关，模型名是逻辑名，映射在网关侧 |
| 云服务锁死 + 素材外泄 | 单机自托管，数据全本地（SQLite + 文件），BYO key |

### 3.2 设计取舍（有意的「不做」）

这些取舍解释了代码里很多"为什么不用 XX"：

1. **不用外部中间件。** 没有 PostgreSQL / Redis / Celery / Ray。任务在进程内用后台线程执行，状态落 SQLite。理由：自托管门槛必须低到"一台小 VPS 就够"。
2. **不做多租户。** CE 固定单本地用户、免登录（`ST_EDITION=ce`，`ST_CONTROL_PLANE_DSN` 强制为空）。多租户/计费/分布式属于 EE，通过端口适配器在运行时注入，**核心代码永不 import 企业代码**。
3. **模型不在本机跑。** 所有推理走网关。本地只有 CPU 轻负载，除非显式装 `world` extra（3DGS / 全景转 3D，需要 GPU）。
4. **画布与流水线是双轨，不是二选一。** 探索在画布，落定回主线；主线的项目也能投影回画布。这是产品层面的核心差异点，也导致 `freezone/` 成为代码量最大的子包（59 个模块）。
5. **每个阶段可独立调用。** 每个阶段都是独立异步任务 + 独立接口，可顺序跑、跳步跑、从检查点续跑，"工具链本身就是产品"。

## 4. 能力边界：CE vs EE

CE（本仓库）覆盖**完整的个人创作能力**；EE（企业版，不在本仓库）覆盖**管理他人 / 向他人收费 / 替他人运维**所需的能力。

| 维度 | CE（本仓库） | EE（不在本仓库） |
|---|---|---|
| 认证 | 本地单用户、免登录 | 多租户认证、RBAC |
| 项目注册 | 本地 SQLite 索引 | 机群登记与路由 |
| 项目访问 | owner-everywhere（自己全都能看） | 租户级权限 |
| 任务执行 | 进程内 inline | Celery 分布式 |
| 取消状态 | 进程内内存 | Redis |
| 用量计量 | no-op | 计量计费 |
| 生命周期 | no-op | PG 连接池 / Redis |
| 审计 | 本地 NDJSON | 审计表 |
| 额度报价 | `cost = 0` | 价格表 |

> 这张表的**代码落点**是 `src/novelvideo/ports/`：每个端口一个 Protocol，CE 默认实现在 `ports/local/`，EE 通过 entry point 组 `novelvideo.ports_bootstrap` 注册。详见 [03 §6](03-核心功能与流程.md#6-端口与适配器六边形架构)。

**校验机制**：`ensure_bootstrap()` 在启动时做双向校验——设了 DSN 却没注册齐 EE 端口 → 拒绝启动；声明 `ST_EDITION=ce` 却给了 DSN → 拒绝启动（矛盾配置）。这是"同一套代码、两个发行物"能成立的硬约束。

## 5. 技术栈总览

### 后端

| 维度 | 选型 |
|---|---|
| 语言 | Python 3.11–3.12（`>=3.11,<3.13`） |
| Web 框架 | FastAPI + Uvicorn（生产可 gunicorn），前缀 `/api/v1` |
| 数据校验/模型 | Pydantic v2 |
| Agent 框架 | PydanticAI（锁定 `pydantic-ai-slim==1.107.0`，见 [04 §1.1](04-依赖与配置说明.md#11-版本锁定的六个坑改依赖前必读)） |
| 存储 | SQLite（`aiosqlite`）+ 本地文件；可选 `psycopg`/`asyncpg`/`pymysql` 供 EE 与外部源 |
| 知识图谱 | Cognee（`==1.0.5`，仅旧项目路径使用） |
| 媒体处理 | ffmpeg（视频合成）、Pillow、edge-tts/dashscope（TTS） |
| 对象存储 | 阿里 OSS（`oss2`）、S3 兼容（`boto3`）——仅"参考图 relay"可选功能需要 |
| 打包/依赖管理 | hatchling + **uv**（`uv.lock` 为唯一真相） |
| 代码质量 | ruff（规则集冻结为 `E4/E7/E9/F`）、pytest + pytest-asyncio、gitleaks |

### 前端

| 维度 | 选型 |
|---|---|
| 框架 | React 19 + TypeScript 5.8 |
| 构建 | Vite 6（`build` / `build:ce` 双模式） |
| 路由 | TanStack Router（**文件式路由 + 代码生成** `routeTree.gen.ts`） |
| 数据层 | TanStack Query（`@tanstack/react-query`） |
| 状态 | Zustand（13 个 store，见 [02](02-目录结构与模块划分.md)） |
| 画布 | `@xyflow/react`（React Flow 12）+ Konva（局部编辑器） |
| UI | Tailwind CSS 4 + shadcn/Radix；`DESIGN.md` 为视觉唯一真相 |
| 3D / 全景 | PlayCanvas、`@photo-sphere-viewer`、`ogl` |
| 国际化 | i18next + react-i18next |
| 测试 | Vitest + Testing Library + MSW |
