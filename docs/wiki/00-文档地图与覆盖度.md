## 2. 第一版 wiki 的问题（逐条）

| # | 缺失 / 不清晰 | 后果 | 第二版补法 |

## 4. 仍然是边界的地方（明确写出来）

诚实标注比假装完整有用。以下四类**本版没有做到逐文件**，原因与替代方案如下：

| 边界 | 原因 | 替代 |
|---|---|---|
| 前端 1,505 个 TS/TSX 未逐个写条目 | 画布域 382 个文件中有大量 30–80 行的编辑器浮层（`*Overlay`/`*Dialog`/`*Content` 三件套模式），逐个描述信息量低、维护成本极高 | [10](10-前端应用.md) 给出子系统分层 + 节点类型注册表 + 12 个核心文件详解；`files/10` 给出全量文件分组清单与命名约定，可按模式推断 |
| EE（企业版）代码不在本仓库 | 本检出是 CE 源码快照，EE 通过 18 个端口接入 | [02 §5](02-架构与分层.md) 列端口契约；EE 侧实现无法文档化 |
| `docker-compose*.yml`、`LICENSES/`、`examples/` 缺失 | 源码快照未包含发行资产 | [13 §2](13-安装部署与运行.md) 给出三条替代路径 |
| 运行期行为（真实延迟、模型输出质量） | 需要实跑与配额 | 文档只写契约与失败模式，性能数据见 `scripts/benchmarks/` |

## 5. 如何使用 `files/` 里的状态标记

条目末尾的标记决定你能否直接相信它：

- `[核实]`——写文档时读过该文件源码，接口名与行为逐条比对过。可直接依赖。
- `[推断]`——只看了签名、文档字符串与调用点，没读函数体。用于判断「这个文件大概干什么」可以，用于判断边界行为不行。
- `[待补]`——源码本身缺少说明（无 docstring、函数名不表达意图），或行为依赖运行期配置。这类文件改动前必须先读代码。

抽查方式：任取一条 `[核实]`，用 `wc -l` 与 `grep` 复核行数与导出名，应一致。

## 6. 反馈与修订

文档与代码同仓，修订走同一个 PR：

1. 改代码的 PR 里同步改对应 `files/` 条目与功能篇（映射见 [15 §2](15-维护与更新.md)）。
2. 新增文件必须补条目，否则 `scripts/check_dco.py` 之外的文档门禁会报缺（见 [15 §4](15-维护与更新.md)）。
3. 发现条目与代码不符：先改文档，再判断是文档滞后还是代码回归。
