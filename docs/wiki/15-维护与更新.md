# 15 维护与更新

文档会腐化，尤其是「逐文件」这种粒度。这一篇给三样东西：改代码时该改哪篇文档的映射表、最容易过期的九处、以及可以自动跑的校验。

## 1. 三条约定

1. **同 commit 更新**：改代码的 PR 必须包含对应文档改动，否则视为未完成。
2. **新增文件必须补条目**：`files/` 下按包归属添加一段，格式见 [files/README](files/README.md)。
3. **不写会过期的内容**：不写「当前是第几版」（会变）、不写「某人说」（会走）、不写「预计下周」（无意义）。版本号只在 README 与 01 出现，且随 release 改。

## 3. 九个易腐点

这些地方「代码一改，文档必错」，优先级最高：

| # | 易腐点 | 为什么容易错 | 对策 |
|---|---|---|---|
| 1 | 端点数（387） | 每次加接口都变 | 用 `docs/wiki/check_links.py --stats` 重算，别手写 |
| 2 | 任务类型数（51） | 新增 runner 就变 | 同上，脚本从源码统计 |
| 3 | 表数（41） | 新增表 | 同上 |
| 4 | 文件行数 | 任何改动都变 | 行数只作规模参考，不要精确断言 |
| 5 | 默认端口（8780） | 改启动脚本 | 只写「默认」，并指向 `start-ce.sh` |
| 6 | 默认配额数字 | 改 `limits.py` | 表格里注明「默认值，见 `limits.py`」 |
| 7 | 前端文件数（1,505） | 每天都在变 | 用脚本统计，或在文中写「约」 |
| 8 | `PushTargetKind` 值数量 | 前后端各一份 | 只写「同步维护」，不写具体数 |
| 9 | 依赖版本锁定 | 换版本时忘改说明 | 锁定项与理由放在同一张表 |

## 4. 自动校验

仓库里提供一个零依赖校验脚本（放在文档目录，随文档一起维护）：

```bash
cd docs/wiki
python check_links.py           # 检查链接、锚点、表格列数、代码围栏
python check_links.py --stats   # 从源码重算统计数字，与文档中的数字比对
```

它检查四类问题：

| 类型 | 规则 |
|---|---|
| 文件链接 | `[x](y.md)` 的 `y.md` 必须存在 |
| 锚点链接 | `[x](y.md#z)` 的 `z` 必须在目标文件的标题 slug 集合里 |
| 表格 | 同一表格内每行的竖线数量一致（漏列会渲染错位） |
| 代码围栏 | 三个反引号必须成对出现 |

CI 里可以加一条（可选）：

```yaml
- run: python docs/wiki/check_links.py
```

### 4.1 统计口径与底稿生成器

所有数字必须是**脚本算出来的**，不能估。两个脚本的分工：

| 脚本 | 产出 | 用途 |
|---|---|---|
| `check_links.py --stats` | 终端打印 10 项统计 | **唯一权威**：与 README §5、00 §1 对照 |
| `dump_inventory.py` | `.inventory.txt`、`.endpoints.txt` | 写 files/0x 与 06 时的底稿 |

```bash
python dump_inventory.py      # 重新生成两份底稿（零依赖，随文档一起提交）
```

`.inventory.txt` / `.endpoints.txt` 是**生成物**，不是给读者看的文档：前者是按目录分组的逐文件行数、docstring、公开类/函数、包内 import；后者是 387 个端点的方法/路径/handler/docstring。它们随时可删可重建，所以没有逐条讲解。

**行数口径**必须与 `wc -l` 一致——数换行符，不要用 `len(text.split("\n"))`。后者会给每个以换行结尾的文件多算 1 行，453 个文件就是虚高 453 行。两个脚本都用 `count("\n")`，改动时别退回旧写法。

**端点口径**限定为 `api/routes/*.py` + `verification/routes.py`，**不含** `api/app.py` 的 3 条基础设施路由（`/healthz` 与两条 `/static` 挂载）。如果要改这个范围，`check_links.py`、`dump_inventory.py`、`06-HTTP-API参考.md` 三处必须同步，否则 387 这个数字会对不上。

## 5. 新增一个文件条目的模板

````markdown
#### `xxx.py` · 123 行 `[核实]`

**作用**：一句话说清它解决什么问题（不是"工具函数"这种废话）。

**关键实现**：核心类 / 函数，带签名的要点。例：`build_x(ctx, payload) -> Result`，内部走 A→B→C。

**输入 / 输出**：读什么（DB 表、文件、参数），产出什么（返回值、写哪张表、落哪个目录）。

**依赖**：上游谁调它，它调谁（写 2–4 个最关键的就够）。

**场景**：什么时候会走到这个文件。

**注意**：反直觉的点、隐含契约、改动的坑。
````

写完自检三条：有没有说「为什么」而不是只说「是什么」；有没有把「显然的东西」写进去占篇幅；标记是否诚实（没读函数体就写 `[推断]`）。

## 6. 重构文档结构时

如果要把 `files/` 拆得更细或合并：

1. 先改 [README §2.5](README.md) 的索引表；
2. 再改 [00 §1](00-文档地图与覆盖度.md) 的覆盖度矩阵；
3. 全局搜索旧文件名，替换链接（`grep -rn "files/0"`）；
4. 跑 `check_links.py`；
5. 确认 `_v1/` 里的历史文档没有被新文档链接（历史文档允许死链，但不该被引用）。

## 7. 归档策略

| 情况 | 做法 |
|---|---|
| 大版本重构（如本次） | 旧文档整体移入 `_v1/`，新文档重建，README 注明 |
| 单篇过时 | 直接改，不留旧版（Git 历史足够） |
| 已删除的功能 | 从文档删除，并在 [00 §2](00-文档地图与覆盖度.md) 记一行「已移除」，避免读者以为漏写 |

`_v1/` 只作对照，不维护、不保证正确。超过两个大版本后可以删除。

## 8. 文档评审清单（PR 里贴）

- [ ] 新增/修改的文件都有条目，标记诚实
- [ ] 映射表（§2）里涉及的篇目都已更新
- [ ] 没有手写的、会变的统计数字（或已用脚本核对）
- [ ] 内部链接与锚点通过 `check_links.py`
- [ ] 表格列数一致、代码围栏成对
- [ ] 示例命令可复制执行（路径、端口、变量名正确）
- [ ] 没有把「实现细节的猜测」写成事实
